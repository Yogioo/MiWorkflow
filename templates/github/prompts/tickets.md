# 把 spec 拆成开发单

你在给一张 GitHub 讨论单拆开发单。讨论单正文里的 spec 区域就是要做的东西；拆出来的开发单交给 `github_dev` 由 Agent 自动开发。
用 `gh issue create` 在当前仓库里建单；仓库代码只读，不改文件、不提交。

## 怎么拆

- 走曳光弹（tracer bullet）式的竖切：每张单是一条端到端能跑通、能单独验证的窄路径，不按层（先全做数据层、再全做界面）横切。
- 每张单小到一个 Agent 一次能做完、审得过；大了就再切。
- 先把依赖想清楚：哪张单做完，别的单才能开始。没有依赖的单尽量多，好并行。
- 不拆「调研」「写文档」这类没有可验证产出的单；验收条件写进各自的单里。

## 每张开发单怎么写

- 标题：一行说清落点。
- 标签：必须贴 `ready-for-agent`；优先级贴且只贴一个 `P0`~`P4`（`P0` 最急，拿不准就 `P2`）。标签不存在就先 `gh label create`。
- 正文按这个结构：

```markdown
## Parent

#<讨论单号>

## What to build

<这张单要做的那条竖切，端到端描述行为，不写实现细节>

## Acceptance criteria

- [ ] <可验证的条件>
- [ ] <…>

## Blocked by

- [ ] #<依赖的开发单号>
```

- Parent 写成普通一行 `#<讨论单号>`，**不要**写成任务列表（`- [ ] #N`），否则开发单会被讨论单挡住、永远不就绪。
- 依赖写成行首任务列表引用 `- [ ] #N`，一行一个，只引用本仓库的单；没有依赖就写 `无`。不要引用讨论单，不要引用自己，不要互相依赖成环。
- 按依赖顺序创建：被依赖的单先建，拿到单号再建依赖它的单。

## 不要做的事

- 不 close、不编辑、不评论讨论单，不改它的标签——讨论单的正文与阶段由工作流来改。
- 不动已有的其他 issue。

## 交回

建完后在 `data.tickets` 里用几行文字列出建了哪些单（单号、标题、依赖）。工作流会去 GitHub 上回查，以实际结果为准。
