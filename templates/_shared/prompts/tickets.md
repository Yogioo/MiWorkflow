# 把 spec 拆成开发单

你在给一张讨论单拆开发单：讨论单里的 spec 就是要做的东西，拆出来的开发单交给 `dev` 由 Agent 自动开发。

**不要碰工单系统**：不建单、不贴标签、不改状态、不发评论。你只交回结构，建单 / 贴标签 / 写依赖由工作流来做。

## 怎么拆

- 走曳光弹（tracer bullet）式的竖切：每张单是一条端到端能跑通、能单独验证的窄路径，不按层（先全做数据层、再全做界面）横切。
- 每张单小到一个 Agent 一次能做完、审得过；大了就再切。
- 先把依赖想清楚：哪张单做完，别的单才能开始。没有依赖的单尽量多，好并行。
- 不拆「调研」「写文档」这类没有可验证产出的单；验收条件写进各自的单里。
- 讨论单要是已经拆过开发单（评论里有「已建开发单 …」那条），只拆 spec 里还没做、也还没建单的部分；
  已有的开发单不要重复建，新单依赖旧单就在正文里写明旧单的工单号（`blockedBy` 只能写本次的 key）。

## 交回的结构

`data.tickets` 是一个**非空数组**，每项：

- `key`：本次内的短编号（`t1` / `t2`…），`blockedBy` 用 key 指别的开发单
- `title`：一行说清落点
- `body`：这张单的正文（Markdown，结构见下）。**不要**在里面写父单与依赖，工作流会加
- `priority`：`'P0'` ~ `'P4'`（`P0` 最急，拿不准就 `'P2'`）
- `review`：`true` 表示这张单开发完要叫审查 Agent 看。这几类单才给 `true`：别的单依赖的地基单，改公共接口 / 共享模块的，
  改配置或数据格式默认值的，删改已有行为的。其余的给 `false`——普通单靠开发者自测 + 工作流验证就够了
- `blockedBy`：被哪些开发单挡着（用 `key`），没有就给 `[]`

`body` 用这个结构：

```markdown
## What to build

<这张单要做的那条竖切，端到端描述行为，不写实现细节>

## Acceptance criteria

- [ ] <可验证的条件>
- [ ] <…>
```

## 依赖的写法

- `blockedBy` 只写本次拆出的开发单的 key，不要写讨论单、不要写自己、不要互相依赖成环。
- 工作流会按依赖顺序建单，并把依赖落成工单系统里的关系（或正文里的引用），你不用管。

## 不要做的事

- 不动讨论单的正文与评论，不改它的阶段标签——都由工作流来改。
- 不动已有的其他工单。

## 交回

最后只回一段 JSON：`{status, choice, reason, data: {tickets}}`，`choice` 用 `tickets`。
